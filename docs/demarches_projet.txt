1. COMPREHENSION MISSION (tech + métier)
--------------------------------------------------------------------------------
METIER
  Banque « Prêt à dépenser » : décider d’accorder ou refuser un crédit conso
  à des clients avec peu d’historique. Un défaut (mauvais client accepté = FN)
  coûte beaucoup plus cher qu’un refus d’un bon client (FP). Hypothèse simple
  retenue : FN:FP = 10:1 (exemple consigne, D-011).

TECH
  Problème = classification binaire (TARGET 0/1) avec proba de défaut,
  puis seuil de décision ≠ forcément 0.5. Pipeline MLOps MLflow exigé
  (tracking → registry → serving) + explicabilité globale et locale
  (phrase mission + notes.txt : chargé d’études doit comprendre le score).

5. MULTI-MODELES + StratifiedKFold + SEUIL (consigne étapes 3–4 partiel)
--------------------------------------------------------------------------------
METIER
  Comparer des familles sous le MÊME critère de coût d’erreur, pas seulement
  l’AUC. Décider qui mérite d’être optimisé ensuite.

TECH
  src/run_cv_baselines.py : StratifiedKFold(5), LR / RF / LGBM / XGB,
  seuil* = argmin coût sur OOF, métriques holdout valid.
  Classement valid coût@0.5 :
    LightGBM 30013 < XGBoost 30421 < LogReg 31666 < RF 32324
  → Champion provisoire = LightGBM (D-013, D-014).


--------------------------------------------------------------------------------
6. OPTUNA SUR LIGHTGBM + RE-SEUIL (consigne étape 4)
--------------------------------------------------------------------------------
METIER
  Améliorer un peu le ranking des risques puis régler le curseur d’acceptation
  (seuil) pour minimiser les pertes FN/FP sur valid.

TECH
  Optuna TPE, 25 trials, objectif = maximiser AUC CV (3 folds), puis éval
  5-fold + seuil* sur valid. Séparation volontaire AUC (HPO) / coût (seuil)
  pour un signal plus propre (D-015).
  Gain : AUC 0.784 → 0.786 ; coût@seuil 0.52 → 29962 (vs 30013@0.5 baseline).

7. EXPLICABILITE SHAP (mission — notes.txt L603–604) — FAIT 2026-10-09
--------------------------------------------------------------------------------
OUI, ça s’applique pleinement au projet. La mission exige d’analyser les
features les plus influentes :
  - de manière GÉNÉRALE (globale)
  - au niveau d’un CLIENT (locale)
pour qu’un chargé d’études comprenne le score.

TECH
  src/run_shap_lgbm.py : TreeExplainer sur champion Optuna.
  Global : summary + bar + CSV mean |SHAP| (n=1500 valid).
  Local : 3 waterfalls (refus clair, accord clair, proche du seuil*).
  Artefacts : reports/shap/ + run MLflow lightgbm_shap_fe_v1.

  Top global observé (mean |SHAP|) :
    1) EXT_SOURCE_2  2) EXT_SOURCE_3  3) EXT_SOURCE_1
    4) CREDIT_GOODS_RATIO  5) ORGANIZATION_TYPE  6) CODE_GENDER
    7) LATE_RATE  …

  Cas locaux :
    - SK_ID 156227 proba≈0.97 → REFUS (y_true=1) ; top EXT_SOURCE_2
    - SK_ID 249554 proba≈0.01 → ACCORD (y_true=0) ; top EXT_SOURCE_2
    - SK_ID 324321 proba≈0.52 → REFUS près seuil ; top CODE_GENDER

METIER
  Global = « en moyenne, quelles infos font monter/baisser le risque ? »
  Les EXT_SOURCE_* (scores externes) dominent — cohérent avec l’EDA.
  LATE_RATE / historiques = signal comportemental de remboursement.
  Local = « pour CE dossier, pourquoi on refuse / accepte ? ».

  POINT D’ATTENTION (à dire en présentation) :
  CODE_GENDER apparaît dans le top global et en local près du seuil.
  C’est une variable sensible (équité / discrimination). Pour OC on la
  documente comme observation du modèle fe_v1 ; en prod réelle on
  discuterait exclusion / monitoring fairlendling avec le métier.
