--------------------------------------------------------------------------------
3. VALIDATION CROISÉE MULTI-MODÈLES + SEUIL MÉTIER
--------------------------------------------------------------------------------
Script : src/run_cv_baselines.py

À quoi ça sert :
  Comparer de façon robuste quatre familles de modèles sous le même protocole :
  validation croisée stratifiée (5 plis), coût métier 10×faux négatifs + 1×faux
  positifs, optimisation du seuil sur les probabilités hors pli (out-of-fold),
  puis évaluation sur le jeu de validation holdout.
  Produit aussi la courbe « coût versus seuil » (artefact MLflow).

Commande (tous les modèles) :

  uv run python -m src.run_cv_baselines

Sous-ensemble (exemple LightGBM et XGBoost seulement) :

  uv run python -m src.run_cv_baselines --models lightgbm xgboost

Runs MLflow créés (un par modèle, statut en principe « terminé » si tout va bien) :
  - logreg_cv5_seuil_opt_fe_v1
  - random_forest_cv5_seuil_opt_fe_v1
  - lightgbm_cv5_seuil_opt_fe_v1
  - xgboost_cv5_seuil_opt_fe_v1

Impact :
  Long (surtout Random Forest) : plusieurs minutes à dizaines de minutes
  Remplit l’expérience credit-scoring-fe_v1 de runs de comparaison
  Écrit reports/cv_threshold_summary.csv
  Artefacts par run : threshold/threshold_cost_curve.png et .csv
  Hyperparamètres = baselines (pas encore Optuna)


--------------------------------------------------------------------------------
4. OPTIMISATION DES HYPERPARAMÈTRES OPTUNA (LightGBM) + SEUIL SUR VALIDATION
--------------------------------------------------------------------------------
Script : src/run_optuna_lgbm.py

À quoi ça sert :
  À partir du champion de l’étape précédente (LightGBM), chercher de meilleurs
  hyperparamètres avec Optuna (objectif : maximiser l’aire sous la courbe ROC
  en validation croisée), puis recalculer le seuil métier optimal sur le jeu
  de validation. C’est le modèle « champion » du projet.

Commande :

  uv run python -m src.run_optuna_lgbm --n-trials 25

Runs MLflow créés :
  - Parent : lightgbm_optuna_fe_v1
  - Enfants nestés : trial_000, trial_001, … (un par essai Optuna)

Impact :
  Long (de l’ordre de 10 minutes ou plus selon la machine)
  Écrit reports/optuna_lgbm_best.json et reports/optuna_lgbm_trials.csv
  Définit le seuil métier retenu (environ 0.52) et les métriques champion
  (aire sous la courbe validation environ 0.786, coût métier environ 29962)
  Artefact courbe seuil aussi sous Artifacts → threshold/


--------------------------------------------------------------------------------
5. SEUIL MÉTIER SEUL SUR LIGHTGBM BASELINE (SANS OPTUNA)
--------------------------------------------------------------------------------
Script : src/run_threshold_on_valid.py

À quoi ça sert :
  Isoler l’effet du seuil : entraîner un LightGBM avec les hyperparamètres
  de baseline (ceux de la validation croisée, pas Optuna), balayer les seuils
  sur le jeu de validation, logger le minimum de coût.
  Utile pédagogiquement pour voir que le minimum peut être à 0.5.

Commande :

  uv run python -m src.run_threshold_on_valid

Run MLflow créé :
  - lightgbm_seuil_valid_opt_fe_v1

Impact :
  Court (quelques secondes à une minute)
  Écrit reports/lgbm_threshold_curve_valid.csv
  Ne remplace pas le champion Optuna

7. ENREGISTREMENT DANS LE MODEL REGISTRY (+ TEST DE CHARGEMENT)

À quoi ça sert :

Runs MLflow créés :

    (il peut y en avoir deux dans l’historique : une première tentative
     en échec sur le schéma des catégories, puis une version corrigée
     avec le wrapper pyfunc — garder la version réussie / la plus récente)

Impact :
  Court
  Crée ou met à jour le modèle enregistré credit-scoring-lgbm
    (version Staging + alias @champion)
  Écrit reports/registry_champion.json
  Les métriques valid_auc / coût affichées sont celles du champion Optuna
  (recopiées), pas un nouvel entraînement « meilleur »


--------------------------------------------------------------------------------
8. SERVING MLFLOW (API HTTP DE PRÉDICTION)
--------------------------------------------------------------------------------
À quoi ça sert :
  Exposer le modèle enregistré derrière une adresse HTTP : on envoie les
  variables d’un client, on reçoit une probabilité de défaut.
  Le seuil métier (0.52) s’applique ensuite côté application
  (si probabilité >= 0.52 alors refus, sinon accord).

Commande (laisser tourner dans un terminal dédié) :

  uv run mlflow models serve -m "models:/credit-scoring-lgbm@champion" --port 5001 --env-manager local --host 127.0.0.1

Endpoint de prédiction :
  POST http://127.0.0.1:5001/invocations
  Corps : JSON au format dataframe_split (features du client)

Impact :
  Aucun nouvel enregistrement MLflow de run d’entraînement
  Processus serveur actif tant que le terminal reste ouvert
  Prérequis : avoir réussi l’étape Model Registry

10. API FASTAPI (partie 2)
--------------------------------------------------------------------------------
À quoi ça sert :
  Exposer le champion LightGBM en HTTP : proba de défaut + décision
  (seuil métier 0.52). Documentation interactive Swagger.

Lancer l’API (terminal dédié) :

  uv run uvicorn api.main:app --host 127.0.0.1 --port 8000

Puis ouvrir : http://127.0.0.1:8000/docs

Tester une prédiction (exemple) :

  uv run python -c "import json,urllib.request; body=open('reports/api_sample_client.json','rb').read(); req=urllib.request.Request('http://127.0.0.1:8000/predict',data=body,headers={'Content-Type':'application/json'},method='POST'); print(urllib.request.urlopen(req).read().decode())"

Tests automatisés :

  uv run pytest tests/test_api.py -q

Docker (Docker Desktop doit être démarré — icône baleine active) :

  docker build -t credit-scoring-api .
  # Port hôte 8001 recommandé : le 8000 est souvent déjà pris sur Windows.
  docker run --rm -d --name credit-scoring-api-run -p 8001:8000 credit-scoring-api

  curl http://127.0.0.1:8001/health
  curl http://127.0.0.1:8001/model/info
  # Arrêt : docker rm -f credit-scoring-api-run

Impact :
  Charge le modèle UNE fois au démarrage (lifespan).
  Écrit des logs JSONL dans logs/predictions.jsonl (ignoré par Git).
  Ne dépend PAS de mlflow.db pour prédire (lit models/champion_lgbm_optuna.onnx).
  Image basée sur requirements-api.txt (onnxruntime, sans LightGBM).

Note consigne : déploiement cloud NON obligatoire — « simulé localement ou réel » suffit.
