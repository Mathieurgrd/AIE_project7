2. PROPOSITION FEATURE ENGINEERING (fe_v1)
--------------------------------------------------------------------------------
Philosophie (3 règles simples) :

  1) D’abord l’historique crédit/paiements, pas les 122 colonnes une par une.
     Pourquoi : le défaut se lit surtout dans le passé de remboursement, pas
     dans chaque FLAG_DOCUMENT isolé.

  2) Avant le split : seulement des calculs « fixes » (âge, ratios, groupby).
     Après le split : tout ce qui *apprend* sur les données (médiane pour
     imputer, modalités pour One-Hot, moyenne/écart-type pour scaler).
     Pourquoi : éviter le **leakage** (fuite d’info du valid/test vers l’entraînement).
     En pratique : si tu calcules la médiane sur TOUT le dataset puis tu splits,
     le valid a déjà « influencée » cette médiane → score trop optimiste.

  3) seed=42 + préfixes BUREAU_/PREV_/… pour retrouver l’origine d’une feature.


2.1 application_train / test (nettoyage déterministe)

  - DAYS_EMPLOYED == 365243 → NaN + flag DAYS_EMPLOYED_ANOMALY
    Pourquoi : ce chiffre est un code « valeur manquante / sans emploi », pas
    une vraie durée d’emploi (~18 % des clients).

  - AGE_YEARS = -DAYS_BIRTH / 365.25
    Pourquoi : l’âge en années est plus lisible que des jours négatifs.

  - EMPLOYMENT_YEARS = -DAYS_EMPLOYED / 365.25 (après nettoyage)
    Pourquoi : même raison, pour l’ancienneté d’emploi.

  - Ratios CREDIT_INCOME_RATIO, ANNUITY_INCOME_RATIO, CREDIT_GOODS_RATIO
    Pourquoi : « combien pèse le crédit / la mensualité par rapport au revenu »
    parle plus du risque que le montant brut seul (aussi présent chez jsaguiar).

  - HOUSING_MISSING = 1 si COMMONAREA_AVG est vide
    Pourquoi : l’EDA montre que les infos immeuble manquent souvent *en bloc* ;
    le fait de ne pas avoir l’info peut être un signal, pas seulement un trou.

  - On garde EXT_SOURCE_1/2/3 tels quels
    Pourquoi : ce sont des scores de risque externes ; en EDA ils séparent déjà
    bien bons / mauvais payeurs.

  - On ne jette pas tout le bloc logement à 60–70 % de NA
    Pourquoi : une colonne très vide n’est pas forcément inutile (surtout avec
    un flag + modèles à arbres qui gèrent les NA).


2.2 bureau (crédits chez d’autres organismes)

  Agg par client (count, sum/mean/max dettes et retards, nb Active/Closed…).
  Pourquoi : connaître l’endettement *ailleurs* et les retards déjà observés
  aide à estimer le risque actuel.


2.3 bureau_balance (historique mensuel de ces crédits)

  Agg en 2 temps (mois → crédit → client) pour ne pas saturer la RAM.
  RAM = Random Access Memory = la mémoire vive de l’ordinateur (là où Python
  charge les tableaux pendant le calcul). Ce n’est pas le disque dur : si un
  CSV de ~27M lignes est lu d’un coup puis joint sans agrégation, la RAM peut
  se remplir → machine lente ou plantage (MemoryError).
  Pourquoi l’agg en 2 temps : savoir *à quelle fréquence* le client était en
  retard mois après mois est utile, mais il faut réduire le volume tôt
  (mois → crédit, puis crédit → client) pour rester dans la RAM disponible.


2.4 previous_application (anciennes demandes chez Home Credit)

  Nb demandes, montants moyens, part Approuvé / Refusé / Annulé…
  Pourquoi : un client souvent refusé (ou toujours approuvé) n’a pas le même
  profil de risque.


2.5 installments_payments (échéances et paiements réels)

  On crée puis on agrège :
  - PAYMENT_DIFF = payé − dû  (négatif = a payé moins que prévu)
  - DAYS_LATE = date paiement − date prévue  (positif = en retard)
  - LATE_RATE = part d’échéances en retard

  Pourquoi : quelqu’un qui paie en retard ou moins que prévu sur d’anciens
  crédits a un comportement **proche** du défaut qu’on cherche à prédire
  (« proche » = même famille de signal métier : mauvaise tenue de paiement,
  pas une preuve directe du TARGET actuel).


2.6 POS_CASH_balance

  Moyenne / max des jours de retard (DPD), échéances restantes, etc.
  Pourquoi : retards déjà vus sur crédits magasin / cash Home Credit.


2.7 credit_card_balance

  Solde, plafond, taux d’utilisation (solde/plafond), retards.
  Pourquoi : une carte très utilisée ou en retard suggère une tension financière.


2.8 Merges

  Left join sur SK_ID_CURR ; on vérifie que le nombre de lignes ne change pas.
  Pourquoi : si le merge multiplie les lignes, le modèle voit plusieurs fois
  le même client → résultats faussés.
  Les NA après merge = « pas d’historique sur cette table » : normal.


3. SPLIT & ARTEFACTS
--------------------------------------------------------------------------------
  - Split 80 % train / 20 % valid, **stratifié** sur TARGET, seed=42.
    Pourquoi : garder ~8 % de défauts dans les deux jeux (sinon un côté peut
    se retrouver avec trop peu de TARGET=1).

  - Même FE sur application_test (sans TARGET).
  - Fichiers : data/interim/*.parquet + data/processed/{train,valid,test}.parquet
    + meta.json
  - Parquet plutôt que CSV : plus compact et plus rapide à recharger.

  - Imputation / One-Hot / scaling sklearn : **après** le split, dans le
    notebook modèle (pipeline LR). LightGBM peut travailler avec catégories
    et NA sans ce preprocessing lourd.
    Pourquoi : le « fit » ne doit voir que le train.


4. CHOIX NON RETENUS (et pourquoi)
--------------------------------------------------------------------------------
  - Copier-coller un kernel Kaggle entier
    Pourquoi : la consigne demande d’analyser/adapter ; un script opaque est
    mauvais pour la soutenance / la pédagogie / le MLOps.

  - Appliquer SMOTE sur tout le dataset avant le split
    Pourquoi : le valid recevrait des clients « synthétiques » ou une
    distribution faussée → on ne mesure plus la vraie perf. SMOTE = seulement
    dans les folds d’entraînement, plus tard.

  - Scaling (StandardScaler / MinMax) sur TOUT le jeu AVANT le split
    Pourquoi — explication détaillée (ligne autrefois trop courte) :
      Le scaler calcule moyenne et écart-type (ou min/max) sur les données
      qu’on lui donne. Si tu le fit sur train+valid mélangés :
        1) la moyenne « voit » déjà les clients du valid ;
        2) tu transformes ensuite le valid avec ces stats ;
        3) le modèle est évalué sur un valid qui a fuité dans le preprocessing
           → AUC trop belle, non reproductible en prod.
      Bonne pratique : fit_transform(train) puis transform(valid/test) seulement,
      idéalement dans un Pipeline sklearn. Pour LightGBM, le scaling est souvent
      inutile (arbres = seuils sur valeurs brutes).

  - Supprimer toutes les colonnes avec > 60 % de NA
    Pourquoi : EXT_SOURCE_1 et le bloc logement montrent qu’on peut garder
    l’info + un flag d’absence plutôt que tout jeter trop tôt.

  - FE type compétition (centaines de features, stacks)
    Pourquoi : hors priorité de fe_v1 (temps, lisibilité, focus coût métier +
    MLflow).

6.bis  COMMENT FIXER LE COÛT FN/FP SANS LE TIRER AU HASARD ?
--------------------------------------------------------------------------------
La consigne dit « par exemple FN = 10 × FP » : c’est un **exemple pédagogique**,
pas une constante économique magique.

Idée : exprimer chaque erreur en **euros attendus** (même unité), puis
ratio = coût_FN / coût_FP.

  Coût d’un FN (mauvais client accepté)
    ≈ perte moyenne si défaut
    ≈ exposition × taux de perte en cas de défaut (LGD)
    Ex. : crédit moyen 150 k€, on récupère 40 % → perte ~ 90 k€.
    (Ou plus simple : moyenne historique des pertes sur dossiers en défaut.)

  Coût d’un FP (bon client refusé)
    ≈ marge / profit attendu qu’on rate sur un bon payeur
    Ex. : marge nette moyenne sur la durée du prêt ~ 9 k€.

  Alors ratio ≈ 90 / 9 = 10 → on **retrouve** 10:1, mais ancré sur des chiffres
  métier, pas sur un doigt levé.

Autres façons non arbitraires :
  1) Atelier risk / métier : consensus documenté « défaut vs refus ».
  2) Données historiques de la boîte (pertes réelles vs marges).
  3) Sensibilité : tester 5:1, 10:1, 20:1 — si modèle/seuil bougent peu,
     le chiffre exact importe moins ; sinon trancher avec le métier.
  4) Appétit au risque / contrainte (ex. rappel minimal) plutôt qu’un ratio euro.

Pour la suite : on garde 10:1 comme hypothèse tracée dans MLflow
(params fn_cost/fp_cost), en attendant validation mentor / vrais chiffres.
Le seuil 0.5 reste à optimiser sous ce coût.
